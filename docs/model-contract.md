# House-model contract

The 3D workspace is driven by a supplied `house-model` package. This document is the contract
between that package and the code in `src/house/`, `src/server/house-model/` and
`src/app/api/house-model/`: what the app may rely on, what it must tolerate, what it persists, and
every place the implementation deliberately deviates from a naive reading of the package.

Source of truth is the code plus `manifest.schema.json` inside the installed package. The original
design pass is `docs/design-notes/house-workspace-3d.md` (reference only; this file and the code
win where they differ).

## 1. The package

Immutable input (CLAUDE.md rule 7). Nothing in the app ever writes inside a package directory
after the install rename.

```
$VH_DATA_DIR/model/current.json          { "modelId": "...", "fingerprint": "..." }
$VH_DATA_DIR/model/<fingerprint>/model.json
$VH_DATA_DIR/model/<fingerprint>/manifest.schema.json
$VH_DATA_DIR/model/<fingerprint>/assets/*.glb
$VH_DATA_DIR/model/<fingerprint>/package.lock.json     written by `pnpm vh-admin model-import <dir>`
```

`fingerprint` = sha256 over the sorted `"<relpath>:<bytes>:<sha256>"` lines of `model.json`,
`manifest.schema.json` and every `assets/*.glb`, truncated to 16 hex characters
(`computeFingerprint` in `src/server/house-model/package.ts`). It is stable across machines and
across a copy, and changes if any packaged byte changes. Because it is content-addressed, a package
swap changes every asset URL and needs no cache purge.

**The real package never enters this repo** (hard rule 1). Tests run against the synthetic fixture
in `tests/fixtures/model/house-model/`, regenerated by `pnpm fixture:model`
(`scripts/make-fixture-model.ts`, deterministic, ~64 kB). Set
`VH_REAL_MODEL_DIR=<dir>` to additionally run the real-package assertions, which are skipped
otherwise.

### 1.1 Validation

`src/house/model/schema.ts` mirrors `manifest.schema.json` field for field, with **loose** objects
(`z.looseObject`) because the JSON Schema sets `additionalProperties: true` — a future revision
must not fail validation for adding a field. `src/house/model/crossref.ts` then returns
*diagnostics* rather than throwing, so a partially broken package still yields a useful setup
state instead of a blank canvas.

Asset **existence** is checked server-side only (the browser cannot `fs.stat`):
`GET .../status` reports per-asset presence, and the client merges that with its own zod +
cross-reference result.

Enum values the app must accept, verified against the real package:

| Field | Values |
|---|---|
| `rooms[].kind` | `room`, `attic`, `void`, **`closet`** |
| `*.certainty` | `measured`, **`derived`**, `inferred`, `unknown` |
| `surfaces[].kind` | `floor`, `wall`, `ceiling`, `other` |

### 1.2 Structural facts the code relies on

Measured from the real package and reproduced by the fixture, so a regression fails a test rather
than the browser:

| Fact | Consequence in code |
|---|---|
| No node carries a transform: world = local = site frame | Loaded roots are added at identity; `matrixAutoUpdate = false` on static shell nodes |
| One material per mesh (nothing shared) | `mesh.material.color` may be mutated directly; `auditMaterials` still clones on a violation and reports `cloned` |
| `defaultColor` is the sRGB encoding of the linear `baseColorFactor` | `material.color.set('#rrggbb')` reproduces the shipped value under three's default colour management. Asserted per surface in `manifest.test.ts` / `scene.test.ts` |
| A mesh node's name **is** the `surfaceId`; an element group node's name is the `elementId`; a floor node's name is the `floorId` | Everything is keyed by manifest id — never by node index or array position |
| Some surface nodes have **no mesh** (degenerate bands) | Every colour / highlight / visibility path tolerates a node with no `.material`; `surfaceMesh` simply has no entry |
| Hierarchy depth is **not** uniform, and `terrain` has a `site` node instead of a building node | Indexing walks by name, never by depth |
| A floor node appears in **more than one asset** (`f-upper` in the upper, roof and structure assets) | `floorNodes` is a `Map<FloorId, Object3D[]>`; floor isolation and explode index every loaded asset |
| Some elements sit outside any floor node | A static policy table (`model/explodeGroups.ts`) assigns every such node to a floor, `roof` or `site`; a test enumerates the package's nodes and fails on an unclassified one |
| `edges-<assetId>` is one object per asset and cannot be split per floor | An asset whose edges span two explode groups hides its edges while exploded, and the UI says so |

## 2. Server routes

All under `/api/house-model/[modelId]/`, all wrapped in `authed()` (rule 2), all serving private
household files that are never in `public/`.

| Route | Cache | Notes |
|---|---|---|
| `GET /status` | `private, no-store` | The discovery hop: hands the client the current fingerprint, per-asset presence and diagnostics |
| `GET /manifest?v=<fingerprint>` | `private, max-age=31536000, immutable`, `ETag`, `Vary: Cookie` | `409 stale_fingerprint` when `?v=` is not the installed fingerprint |
| `GET /assets/<assetId>?v=<fingerprint>` | same | `assetId` is an allow-list lookup in the manifest; the resolved path must pass `safeJoin` (no traversal, no symlink, `assets/<name>.glb` only) |
| `GET`/`PATCH /colors` | `private, no-store` | Surface colour overrides |
| `GET`/`PUT /placements`, `DELETE /placements/<id>` | `private, no-store` | Equipment placements, **including the mount** (§3.1) |
| `GET`/`PUT /routes`, `DELETE /routes/<id>` | `private, no-store` | Infrastructure runs with their polyline. `DELETE` is **soft** (§3.4); `?hard=1` erases a wrongly drawn line. `GET ?options=projects` serves the inspector's project picker |
| `GET`/`PUT`/`DELETE /endpoints` | `private, no-store` | Manifolds, shutoffs, meters, panels, patch ports. `DELETE ?id=<endpointId>` |
| `GET`/`PUT`/`DELETE /annotations` | `private, no-store` | Pins: notes, measurements, warnings, to-dos, photo viewpoints. `DELETE ?id=<annotationId>` |

`Cache-Control` is always `private`, never `public`: a shared cache must never hold these bytes.
`ModelPackageError` is mapped to a status by `currentPackageForRequest`, so "no package installed
yet" answers `409 no_package` (a setup state) rather than a generic 500.

### 2.1 Client loading tiers — a documented deviation

`loadByDefault` governs **whether** an asset is part of the default set. It does not govern the
order in which the client fetches them. `planTiers` schedules:

| Tier | Assets | Gate |
|---|---|---|
| 0 shell | shell + roof + details | blocks `interactive` |
| 1 site | terrain | after `interactive` |
| 2 structure | structure assets | only when the structure layer is on (off by default) |
| 3 scan | scan references | explicit opt-in (`loadByDefault: false` in the package too) |

This is a client-side scheduling decision, recorded here because it deviates from reading the
manifest's ordering as a load order. On a phone, tiers 2 and 3 are never loaded at all.

`Promise.allSettled`, never `Promise.all`: one failed asset degrades the workspace
(`phase: 'degraded'`, the asset named in the setup panel) instead of failing it.

## 3. What the app persists, and what it does not

Runtime data references `modelId` + semantic ids + **physical** site metres, rounded to
millimetres. Exploded and cutaway views are presentation transforms and have no storage anywhere
(rule 7).

| Data | Table | Coverage |
|---|---|---|
| Surface colour | `surface_color_override` | **Complete.** `(modelId, surfaceId) → #rrggbb`, plus the `model_revision_id` the choice was made against. Reset deletes the row, restoring the manifest's `defaultColor` |
| Equipment placement | `asset_placement` | Geometry **and the mount** — one gap left, see §3.1 |
| Infrastructure routes | `infra_route`, `infra_route_point` | **Complete.** Polyline in physical metres with per-point floor/room, medium, certainty, lifecycle + dates, depth/offset, project, photos via `attachment_link` |
| Infrastructure endpoints | `infra_endpoint` | **Complete.** A coordinate is optional: an endpoint may be location-only |
| Model annotations | `annotation` | **Complete.** Pins with an optional coordinate, plus a measurement value and unit |
| Renovation projects | `project`, `project_link` | **Complete.** Costs in cents, before/after files by role, links validated in the service layer |

### 3.1 Placement coverage

`asset_placement` stores `model_node_id` (the room, or the floor when the point falls outside every
room's footprint), `pos_x/y/z`, `rot_yaw_deg`, `placement_kind`, and — since migration
`0002_sad_raza` — the **mount**: `mount_kind` (`floor | wall | ceiling | free`),
`mount_surface_id`, `mount_height_m`, `mount_offset_m`, plus `location_note` and
`photo_attachment_id`. A wall-mounted sensor now keeps the record of *which* wall.

Two documented consequences:

- `mount_height_m` is measured from the **resolved room's own** `floorElevation`, not from the site
  datum, so "1.4 m up the wall" means the same thing on every floor. A row written before these
  columns existed has no stored height and the endpoint still derives it the old way, so old rows
  answer the same numbers they always did.
- The workspace's `PlacementMount` union only knows `floor` and `wall`. A `ceiling` mount is
  therefore **answered** as a wall mount on its ceiling surface and a `free` mount as a floor mount
  at its height — the numbers are identical, only the noun is coarser — and the true value travels
  beside it as `mountKind`/`mountSurfaceId`/`mountHeightM`/`mountOffsetM`.

`partialFields` is now `["entityId"]`: the HA entity link is a row in `asset_ha_link`, owned by
another module. A placement says where a thing sits, not what it reports.

### 3.2 The `viewMode: "normal"` rule

Every write that carries a coordinate — placements, routes, endpoints, annotations — must state
`viewMode: "normal"`; anything else is refused with `422 presentation_view_mode`. Defence in depth,
three layers:

1. Entering edit mode animates `explode.gap → 0` and sets `explode.locked = true`; the control is
   disabled with "Exploded view is off while placing equipment".
2. The save path reads the edit draft's `physical` triple and **never** `object.position`. Floor
   snapping derives Y from `room.floorElevation`, so even a hit point taken from an offset floor
   group produces the physical value (asserted in `tests/unit/house/edit.test.ts`).
3. A dev-only assertion (`assertPhysicalY`) checks `worldY − groupOffset ≈ draft.physical[1]`
   before the write is dispatched, and the endpoint rejects a non-`normal` view mode.

### 3.3 Package swap / model correction

Nothing is auto-migrated. `model/reconcile.ts` takes the ids persisted data references plus a
`{ modelId, fingerprint, coordinate }` stamp and reports `unknownSurfaceIds`, `unknownRoomIds`,
`unknownElementIds`, `unknownFloorIds`, `outOfBoundsPositions`, `modelIdChanged` and
`coordinateSystemChanged`. Any non-empty result is a decision for a human. A changed fingerprint
alone is *not* a reconciliation — the same ids in a new build are fine. `GET /colors` already
reports rows whose `surfaceId` the current package no longer knows in a separate `stale` array and
never applies them.

### 3.4 Routes: what is stored, and the two translations

`PUT /routes` takes the polyline in physical site metres, rounded to millimetres, plus the honesty
fields that decide how it is drawn. Two shapes meet at this endpoint, and neither is allowed to
lose information:

| Workspace (`Route`) | Table | Translation |
|---|---|---|
| `system` + `kind` | `infra_route.medium` | A medium has exactly one system and one kind (`src/features/projects/infraMedium.ts`). Going the other way, an explicit `medium` wins, and a `system`-only write **keeps the row's existing medium** when it still belongs to that system — so re-saving a `hot_water` run from the workspace does not turn it into cold water |
| `widthM` / `diameterM` | `infra_route.nominal_size` | Canonically spelled `Ø125 mm` / `W600 mm`, so a size the workspace set round-trips exactly; text a human typed ("DN20", "Cat6a") is stored verbatim and yields no numeric size (`nominalSize.ts`) |
| `segments[i]` (per span) | `infra_route_point.floor_id` / `room_id` (per point) | Point *i* carries the place of the span that starts at it; the last point inherits the previous span's. This is what makes a riser between floors representable |
| `endpoints[]` | `from_endpoint_id` / `to_endpoint_id` | An endpoint naming a piece of equipment is answered as `{kind:'equipment', placementId}` via that equipment's body placement; everything else is `{kind:'free'}`. The workspace's surface+uv variant has no column |
| `renovationId` | `infra_route.project_id` | Same thing under two names; both are accepted on write |

`partialFields` is `["kind", "endpoints", "segments.roomId"]`: `kind` is derived rather than stored,
and the two endpoint descriptors above are coarser than what the workspace can express.

A route whose floor, room or offset surface the **current** package no longer knows is returned with
those ids nulled, listed in `stale`, and flagged `needsReconciliation` — reported, never guessed at
or dropped, exactly as `GET /colors` already does for a surface id.

### 3.5 Deleting a route is soft

`DELETE /routes/<id>` sets `lifecycle = 'removed'` and stamps `removed_on` (keeping an existing one:
re-deleting must not rewrite history). The polyline, the photos and the project link all survive,
because a pipe that was cut out in 2019 is not a mistake to erase — it is the answer to "why is
there a capped stub behind this panel?", and it is what the renovation-date filter reads.

`?hard=1` is for a line that was drawn **wrongly**: a mis-click, a duplicate, a run that turned out
to be somewhere else. That takes its points (cascade) and its attachment links (explicitly, since
SQLite cannot declare a polymorphic FK) with it.

`isRunVisibleOn` (`src/features/projects/renovationDate.ts`) is the pure predicate behind the
filter, and its asymmetry is deliberate: an **installed** run with no install date stays visible
(it exists, and nothing says it postdates the viewed day), while a **removed** run with no removal
date and a **planned** run with no install date are hidden as soon as a date is set — neither can be
placed on a timeline without inventing a fact.

## 4. Colouring

Room-facing surfaces are `roomId === room.id && kind ∈ {floor, wall, ceiling}`. **Filtering is by
`kind` alone, never by `role`** — proven against the real package: every excluded role
(`reveal`, `door-leaf`, `railing`, `step`, `wall-top`, `plinth`, `exterior`, `exterior-ledge`)
already has `kind: 'other'` or no `roomId`, while `dormer-front-wall` and `dormer-ceiling` are
legitimate room surfaces that a role filter would wrongly skip.

`planRoomColors` additionally refuses to touch a surface whose `roomId` is not the room being
planned, so an authoring mistake in `rooms[].surfaceIds` shows up as a `W_ORPHAN_SURFACE`
diagnostic instead of a visible colour bleed. Every room's plan is pairwise disjoint from every
other room's — proven as a data property in `colorPlan.test.ts`.

Selection and hover use `material.emissive` + `emissiveIntensity`, never `material.color`, so a
highlight can never leak into a persisted colour and the override stays the single writer of
`color`.

## 5. Rendering invariants

`frameloop="demand"`: nothing renders unless something asks. The complete list of triggers that
must call `invalidate()`:

- camera controls active or transitioning (the `useDemandFrames` pump);
- a hover change or a selection change (painted synchronously in the pointer handler, before React
  hears about it);
- a colour plan that actually touched a material;
- a visibility plan applied;
- a cut height / vertical cut change;
- each frame of an explode tween;
- an asset finishing loading and being indexed;
- layer toggles and route/marker data changes;
- a marker `instanceColor` change from Home Assistant — **only** when a colour actually changed;
- a canvas resize or dpr change;
- an edit-draft change (including the snap indicator).

Everything else — label text, badge classes, inspector renders, tooltips — is a DOM write and must
**not** invalidate. A temperature reading must not wake the GPU. `__vh.invalidateCount()` exists so
the idle test can assert that.

Other fixed choices: `localClippingEnabled = true` (per-material clipping planes); exactly two
clipping planes allocated per explode group for the life of the scene, "off" being a constant
beyond the model bounds, so the shader never recompiles; `NoToneMapping`, so a persisted hex
matches what the user picked; no shadows; no `three-mesh-bvh`; scan references are non-pickable.

## 6. Recorded deviations from the design note

1. **Ids are plain string aliases, not branded types** (`model/types.ts`). Manifest data arrives
   from zod as plain strings, and every id also travels through the URL, the DOM, the store and
   SQLite; a nominal brand would add casts at every boundary without catching a real class of bug
   (ids are never arithmetic and never mixed with user text).
2. **Client load tiering** deviates from the manifest's `loadByDefault` ordering (§2.1).
3. **Routes and placements are persisted** (§3.4, §3.1). `Route.kind` is derived from the stored
   medium rather than stored, and the numeric size lives inside `nominal_size` text — both listed
   in `partialFields` rather than hidden.
4. **Wall-snapped positions are rounded to millimetres, not re-snapped to the 5 cm grid.** The grid
   applies to `u` and `height` in the wall's own frame; re-snapping world X/Z afterwards would eat
   the 2 cm standoff and leave the marker co-planar with the wall it is mounted on.
5. `react-hooks/immutability` is disabled in the five files that publish imperative handles onto
   the `HouseRuntime`. The runtime is a deliberately mutable, non-reactive box passed through
   context; the React Compiler rule assumes hook return values are immutable, which is exactly the
   assumption this design breaks on purpose. The alternative is putting `Object3D`s in React state.

### 6.1 Follow-ups this slice deliberately left open

Each of these is a small, known change in a file outside the persistence slice, recorded here so it
is a decision rather than an oversight:

- **`useSceneSync.ts` still filters only `removed` routes by date.** `isRunVisibleOn`
  (`src/features/projects/renovationDate.ts`) is the tested predicate that also handles `planned`
  and out-of-range install dates; swapping the inline expression in the routes effect for it is one
  line, in a file this change does not own. The inspector already reports the predicate's answer
  ("Drawn now"), so the two cannot disagree silently.
- **`Inspector.tsx` does not route `selection.kind === "annotation"` yet.**
  `inspector/AnnotationInspector.tsx` exists and is complete; wiring it is one `case`.
- **`/house?project=<id>` is not read by `HouseWorkspace`.** The projects page emits it and appends
  `&sel=route:<id>` for the project's first linked route, so the "Show in house" link does
  something real today. Filtering routes and placements by project needs a store field and a
  `urlSync` key.
- **CSV export serves one dataset per request.** One HTTP response cannot be six files;
  `?format=csv` answers a `_manifest.csv` index and `?format=context` the envelope to file beside
  them. A single zip is the follow-up.
- **`project_link` dangling links are surfaced, not swept.** The detail page shows a link whose
  target has disappeared as **Missing** with its raw id; the nightly integrity job that reports them
  into `app_alert` (design §1.9) is not written yet.

## 7. Honest caveats

- **True north is `inferred`.** Plans render in model orientation with an explicitly-labelled
  inferred north arrow. Nothing is silently rotated.
- **A building may carry a recorded placement uncertainty** (the package's own `issues[]`). The
  inspector shows it, because an equipment position recorded there inherits it.
- **A drawn route line is not proof of a concealed installation.** Confidence is carried by dash
  pattern *and* opacity *and* words in the inspector. The exact sentence is one constant,
  `CERTAINTY_LEGEND` in `house/components/routeEditor/RouteFields.tsx` — "a precise-looking line is
  not proof of a verified concealed installation" — so it cannot be softened in one place and not
  the other, and a test asserts it is shown.
- **Exploded + cutaway composition** relies on per-group clipping-plane pairs tracking each group's
  offset. If it ever misbehaves, the fallback is one line of UI logic: make the two mutually
  exclusive.
- **The performance budgets in the design note are budgets**, computed from the package and the
  producer's reference run — not results this implementation has already demonstrated on the target
  machine.
